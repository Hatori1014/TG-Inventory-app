# Technical decisions

> Source: `plan-inicial-proyecto-inventario.md` and its build history. There are no code commits to extract decisions from — the repository doesn't exist yet. These are the decisions made during the planning phase, with their rationale and the discarded alternatives as they were discussed. Versión en español: `decisiones.md`.

**ADR-01 — Backend: NestJS**
Discarded: .NET (C#/ASP.NET Core). Why: same language (TypeScript) as the Angular frontend, native modular architecture that fits the hexagonal design, decorators (`@Roles`, Guards) convenient for RBAC.

**ADR-02 — Database: PostgreSQL**
Discarded: NoSQL as the primary option. Why: the domain is strongly relational (suppliers↔purchases↔products↔locations↔movements) and needs strong transactional integrity.

**ADR-03 — Architecture: modular monolith (hexagonal per module)**
Discarded: microservices. Why: the defined scale (dozens of users/locations) doesn't justify the operational complexity of microservices; the modular design allows extracting a service later if needed.

**ADR-04 — ORM: Prisma**
Discarded: TypeORM (mentioned as a valid alternative, not the default choice). Why: end-to-end schema typing, simple migrations, better DX.

**ADR-05 — Methodology: adapted Scrumban (not team Scrum)**
Discarded: classic Scrum with 2-week sprints and daily ceremonies. Why: the project is built by a single person, part-time, weekends only — team ceremonies don't apply.

**ADR-06 — Roadmap: 5 incremental MVPs**
Discarded: a single 23-story MVP with external validation only at the end (~8-10 months with no feedback). Why: reduces the risk of building in the wrong direction for months without real validation; allows 4 external checkpoints along the way instead of 1.

**ADR-07 — Inventory movements as the source of truth (immutable ledger)**
Discarded: keeping only a directly-editable "current stock" table. Why: full traceability (who, when, what) and lets stock be reconstructed from history if inconsistencies appear.

**ADR-08 — Configurable approval flow (`ApprovalFlow`)**
Discarded: a fixed `approverId` field with no further structure on `Request`. Why: the user confirmed there's a single approver today but it may become multi-level (direct manager → Inventory Admin) — this design doesn't require a schema migration when that happens.

**ADR-09 — Repository: monorepo**
Discarded: separate repos for backend and frontend. Why: a single developer benefits from one commit history and one PR per functional change, even when it touches both layers.

**ADR-10 — Image storage: Cloudflare R2**
Discarded: storing uploaded files on the application server's disk. Why: egress is always free (unlike S3), and it avoids the attack vector of malicious file uploads landing directly on the server (HU-27).

**ADR-11 — Priority reclassification after backlog validation**
HU-09 (batches), HU-12 (alerts panel), HU-14 (price comparison), and HU-24 (dependency scanning) moved from "Should" to "Must" when validated against the user's original request. Why: they were part of the functional core requested in the first message, not optional enhancements.

**ADR-12 — Code language: English (everything), with an explicit UI exception**
Discarded: keeping the Spanish used in the first draft of `schema.prisma` and in code comments. Why: it's the industry standard and the native language of the whole ecosystem (NestJS, Angular, Prisma). Correction applied retroactively: the local DB was reset and the initial migration regenerated in English. The UI visible to the end user is an explicit exception — it stays in Spanish because the app's users speak Spanish (see `conventions.en.md`).

**ADR-13 — Documentation (`docs/`): bilingual, Spanish + English**
Discarded: Spanish-only (what existed before this decision) or English-only. Why: the code and repository need to be readable in English (industry standard, ADR-12), but communication with the functional stakeholder and business design happen in Spanish. File convention: the unsuffixed name is the Spanish (original) version, `.en.md` is the English translation.

**ADR-14 — UI: language switcher (ES/EN) and light/dark mode**
Added to the backlog as Epic 9 (HU-29, HU-30), explicitly flagged to be tackled **last**, after MVP 4 — not part of the user's original scope and doesn't block any business functionality. See plan section 3 and the Trello board.

**ADR-15 — Staging/production migrations: manual, not automated in deploy**
Discarded: running `prisma migrate deploy` automatically on every push, either by adding it to Render's *Start Command* or via a `cd-deploy.yml` workflow. Why: the chosen CD model (plan section 9.2, native Vercel/Render auto-deploy) doesn't orchestrate any "migrate before starting" step unless explicitly wired in — and for a single developer, while the schema is still changing often (Iteration 0-1), having a manual checkpoint (`npm run prisma:migrate:staging`) before touching the shared database is safer than letting it fire unsupervised on every push. Same reasoning already applied to the ban on `migrate dev` against staging/production (see `CLAUDE.md`).
[PENDING: revisit this decision once the application is stable and schema migrations are infrequent — at that point, evaluate moving `npx prisma migrate deploy` into Render's Start Command to automate it]

**ADR-16 — Documentation (`docs/`): organized into subfolders by type**
Discarded: all files loose in the `docs/` root, distinguished only by the `.en.md` suffix (ADR-13's original approach). Why: once diagrams (PNGs) and the Claude Design reference-export folder were added, mixing everything at a single level became hard to navigate. Final structure: `docs/esp/` (Spanish), `docs/en/` (English), `docs/Diagrams/` (architecture/flow diagrams), `docs/Design/` (Claude Design reference exports only — the live prototype stays in its own workspace, its raw HTML/CSS/JS is never copied into `frontend/`). ADR-13 (bilingual) still applies within `esp/` and `en/`. See `CLAUDE.md`.

**ADR-17 — DDD tactical patterns inside the hexagonal architecture**
Discarded: (a) leaving `domain/` as a container of anemic entities (data only) and moving all business logic into the use-case; (b) adopting full strategic DDD (bounded contexts, context mapping, formal ubiquitous language per subdomain). Why: (a) — the hexagonal architecture already decided (ADR-03) and the repository-interface-as-port convention (`conventions.en.md`) already point toward a DDD-friendly design; leaving the domain anemic wastes that and complicates TDD on critical logic (plan section 5), because tests end up exercising the whole use-case (with repository mocks) instead of the isolated, pure business rule. (b) — the project's domain is single and bounded (modular monolith, a single developer); multiple bounded contexts would add coordination complexity with no real benefit at this scale.
Scope adopted — tactical patterns only, inside the `domain/` that already exists per module:
- **Entities** (`*.entity.ts`) with behavior: rules that depend only on their own data live there, not in the use-case.
- **Value Objects** (`*.value-object.ts`, new): immutable, self-validating on construction (e.g. a stock quantity that can't be negative).
- **Domain Services** (`*.domain-service.ts`, new, in `domain/services/`): pure business rules that don't belong to a single entity (e.g. calculating the resulting stock from a movement history).
- **Repository interfaces** (`*.repository.interface.ts`) as ports — already defined, unchanged.
The use-case (`application/`) stays an orchestrator: it does IO via the repository, delegates the actual rule to `domain/`, and holds no business logic of its own — this explicitly extends to the use-case the prohibition `conventions.en.md` already applied to controllers. Concrete example (the `inventory` module) in `architecture.en.md`.

**ADR-18 — Module boundaries: only via the application layer, enforced with lint**
Discarded: relying solely on convention/code review to keep module isolation. Why: with a single developer and no third-party review, coupling can slip in unnoticed until it hurts — with one shared `schema.prisma`/`PrismaClient`, nothing at the ORM level stops a module from directly importing another module's Prisma repository, bypassing its `application` layer. Rule: a module NEVER imports `domain/` or `infrastructure/` from another module — it may only call the services exported by the owning module's `*.module.ts` (`application` layer).
Enforced with `eslint-plugin-boundaries` (v7) in `backend/.eslintrc.js`, not just by convention — lint fails (and therefore CI, `ci-backend.yml`, since it runs `npm run lint`) if a module imports `domain/` or `infrastructure/` from another. Verified with a test fixture: a same-module import passes clean, a cross-module import fails with the ADR's message (fixture discarded after confirming, doesn't live in the repo).
Future evolution path if the project grows: split each module into its own Postgres schema (same server, no deploy change) as an intermediate step before considering extracting a module into its own service — not implemented now, documented here as an option.

**ADR-19 — Required CI checks: always triggered, real work gated by path internally**
Discarded: (a) keeping `ci-backend.yml`/`ci-frontend.yml` with `paths: ['backend/**']`/`['frontend/**']` on the trigger, as TT-07 left them. Why discarded: branch protection (TT-02) requires the `backend`/`frontend` checks to pass, but a required check that never fires (because the trigger's `paths:` filtered it out) doesn't count as "passed" — GitHub leaves it "Waiting" indefinitely, and the only way through is an admin bypass. In practice, every PR that only touched `docs/` in this session (ADR-17, the TT-16 quoting gotcha) needed a bypass — exactly the shortcut TT-02 was meant to prevent. (b) simply dropping `paths:` from the trigger and letting full `npm ci` + lint + build + test run on every PR even when there's nothing to check — works, but wastes CI minutes and slows down every docs-only PR for no reason.
Solution adopted: drop `paths:` from the trigger (the job always runs, so the required check always reports), and add a `dorny/paths-filter@v3` step at the start of each job that detects whether `backend/**`/`frontend/**` changed. Every real work step (`npm ci`, lint, tests, build, audit) is gated with `if: steps.filter.outputs.<backend|frontend> == 'true'`. Result: a docs-only PR makes the job run and report success in seconds (no real steps), satisfying branch protection without a bypass; a PR that does touch `backend/`/`frontend/` still runs the full pipeline as before. `dorny/paths-filter` is already covered by the existing `github-actions` ecosystem entry in `dependabot.yml` (no changes needed there).

**ADR-20 — Concurrency control on `LocationStock`: optimistic locking with bounded retry**
Discarded: (a) `SELECT ... FOR UPDATE` (pessimistic locking) inside the Prisma transaction — holds the row lock until commit, more expensive under serverless Postgres with cold starts (Neon, TT-16), and not justified at this scale (dozens/hundreds of users, real conflicts infrequent); (b) returning `409` immediately on the first conflict, with no automatic retry — worse UX for the common case (an isolated conflict, not a sustained race), pushing a retry onto the frontend that the backend can resolve on its own.
Solution adopted: a `version Int @default(0)` column on `LocationStock` (migration `20260813180448_add_location_stock_version`), incremented on every successful `UPDATE`. The future movements use-case (HU-08/HU-16/HU-17, not implemented yet — Iteration 0) must use `updateMany({ where: { id, version }, data: { ..., version: { increment: 1 } } })`; if `count === 0` (another process updated first) it re-reads the stock and retries from scratch, up to 3 times, before returning `409 Conflict` to the client. Reusable generic utility in `backend/src/common/utils/optimistic-lock.util.ts` (`withOptimisticLock()`), covered by TDD (critical domain logic, see `conventions.en.md`) — no real consumer yet since no business use-case exists, ready for whichever HU implements stock updates first.

**ADR-21 — Idempotency on critical writes: a Postgres unique constraint, not Redis**
Discarded: (a) disabling the submit button on the frontend as the only protection — that's UX, not a guarantee (same principle as RBAC: never rely on the frontend alone); (b) Redis with a TTL for idempotency keys — typical at larger scale, but adds a new piece of infrastructure (outside the TRD's technical constraints: "no cache/Redis, not planned for the MVP") that Postgres already solves with a unique constraint.
Solution adopted: an `IdempotencyKey` table (unique `key`, `endpoint`, `response` as `Json`, `createdAt`) — migration `20260813181409_add_idempotency_key`. Reusable pattern: an `@Idempotent()` decorator (`backend/src/common/decorators/idempotent.decorator.ts`) marks a critical endpoint; `IdempotencyInterceptor` (`backend/src/common/interceptors/`) requires the `Idempotency-Key` header, returns the already-stored response if the key exists (without re-running the handler), and handles the race between two concurrent requests sharing a key (Postgres unique constraint, code `P2002`) by returning whichever response won the insert instead of failing. Covered with 5 unit tests (mocked `PrismaService`/`Reflector`/`ExecutionContext`). No real consumer yet (Iteration 0); ready for HU-08, HU-13, HU-15, HU-16.

**ADR-22 — Soft delete: `deletedAt` only where a real story needs it, never preemptively**
Origin: a finding during TT-20 (index review), formalized as TT-22. Discarded: (a) generalizing `deletedAt DateTime?` across all 17 models at once — most of them (`RolePermission`, `ApprovalFlow`, `AuditEvent`, `InventoryMovement`, `LocationStock`, `PurchaseItem`, `RequestItem`) are link tables, config, or the immutable ledger (ADR-07); they have no lifecycle of their own that a user "deletes", and adding the field to them would be speculative work with no story consuming it; (b) continuing to extend the `status` pattern (an `active`/`inactive`/… enum) case by case for everything still missing it — that conflates two different concepts: `status` is business state (a discontinued product is still a real product, with history), while a soft delete answers "the user asked to remove this record" — forcing everything through `status` fails to distinguish the two when it matters (e.g. a supplier "deleted by mistake" vs. one that's legitimately inactive).
Decision: once the first real story defines a "delete" action on a model that doesn't already have `status` (`User`/`Location`/`Product`/`Supplier` stay exactly as they are, untouched), that specific model gets a `deletedAt DateTime?` field, and normal reads exclude it via a Prisma Client extension (`$extends`) that automatically filters `deletedAt: null` on `findMany`/`findFirst`/`count` — not a hand-repeated `where: { deletedAt: null }` in every use-case (same spirit as TT-19: don't reimplement a shared pattern in every call site). Never applied to `InventoryMovement` or `AuditEvent` (they're the historical record, ADR-07), nor to link/config tables (`RolePermission`, `ApprovalFlow`), nor to derived rows with no lifecycle of their own (`LocationStock`, `PurchaseItem`, `RequestItem` — deleted or orphaned together with their parent, never individually). None of this is implemented now — it's an architecture decision for whenever the first story needs it, not a code task for this iteration.

**ADR-23 — Administrable catalogs (`Category`, `Unit`): their own table, not free text, not an enum**
Origin: TT-23 finding (2026-08-14), from a user request validating whether the schema lets a role administer "catalog tables" from the frontend. Discarded: (a) keeping `Product.category`/`Product.unit` as free `String` fields (HU-28's original design) — with no dedicated table there's no way to avoid duplicates/typos ("Groceries" vs "groceries"), to deactivate a value without touching existing products, or to offer a controlled selector in the frontend; (b) modeling them as a Prisma enum (same pattern as `ProductStatus`/`MovementType`) — an enum needs a migration + redeploy to add a new value, exactly the opposite of "a role administers this from the frontend".
Solution adopted: `Category` and `Unit` as real tables (same pattern as `Role`; precedent in `ApprovalFlow`, ADR-08), each with a unique `name` and a `status` (`active`/`inactive`) to deactivate without deleting — migration `20260814045501_add_category_unit_catalogs`. `Product.category`/`Product.unit` (`String`) become `Product.categoryId`/`Product.unitId` (FK): `unitId` required (same as `unit` before), `categoryId` optional (same as `category` before). No data to migrate (Iteration 0, no business story implemented yet). RBAC: the same role that administers products (Inventory Admin, HU-28) administers these catalogs — no change needed to the permission model, since `Permission` (`module`/`action`) is already generic and supports adding `categories`/`units` as new modules with no migration. Planned endpoints (`/categories`, `/units`, same pattern as `/roles`) documented in the plan, section 7.4 — controller/service implementation deferred to whenever HU-28 gets implemented (outside TT-23's own scope, which was only the design decision).
General precedent going forward: data gets modeled as a **table** when (1) an admin needs to create/edit values without depending on a deploy and (2) the value doesn't change backend behavior. It gets modeled as an **enum** when code depends on the exact value for its logic (e.g. `MovementType` drives stock calculation — opening it up as a catalog would leave the backend not knowing what to do with a new value).

**ADR-24 — Authentication (HU-01): stateless JWT with no refresh token, manual credential validation, global guards with `@Public()`**
Origin: first business story implemented (2026-08-14), after closing TT-01 through TT-23. Discarded: (a) `passport-local` for the credentials step — indirection with no real benefit for a single JSON endpoint (`POST /auth/login`) with a `class-validator`-checked DTO; not installed, password comparison (`bcrypt.compare`) happens directly inside `LoginUseCase`. (b) Refresh token / renewable session — adds state (a token table, revocation logic) the TRD doesn't ask for in the MVP; HU-19 (password policy) and HU-20 (lockout on failed attempts) are already planned as separate stories, so a single access token with a configurable `JWT_EXPIRES_IN` (environment variable, not hardcoded) is enough for this round. (c) `httpOnly` cookie for the token — would require cross-site CORS (`SameSite=None; Secure`) plus additional CSRF protection, since frontend (Vercel) and backend (Render) are different origins; the Iteration 0 scaffold already assumed `localStorage` + an `Authorization: Bearer` header (`auth.interceptor.ts`, `role.guard.ts` were written that way from the start).
Solution adopted: `passport-jwt`/`JwtStrategy` protects only routes after login and **never re-queries the database on each request** — it trusts the signed claim (stateless). Explicitly accepted trade-off: a user blocked by an admin (`User.status`) keeps access until their current token expires; partly mitigated by keeping `JWT_EXPIRES_IN` short (configurable per environment, not hardcoded), not fully solved until HU-20 lands. `JwtAuthGuard`/`RolesGuard` are registered **globally** (`APP_GUARD` in `auth.module.ts`) — any new endpoint requires a valid JWT by default unless explicitly marked `@Public()` (new decorator, `backend/src/common/decorators/public.decorator.ts`; applied to `POST /auth/login` and to `GET /health`, which would otherwise break Render/CD monitoring) — secure by default instead of opt-in per controller. JWT payload: `sub`/`email`/`name`/`role` (the role's name, not `roleId`, because `RolesGuard` already compares `user?.role` as a string against `@Roles(...)`). Same generic error message for a missing user, a wrong password, and a blocked user (avoids enumeration). No `GET /auth/me` endpoint is created — the frontend restores its session by decoding the JWT payload it already stored in `localStorage` (`atob()`, no `jwt-decode` dependency installed); no `POST /auth/logout` either, that's a 100% frontend action since the token is stateless. No user existed in the database before this HU — `backend/prisma/seed.ts` is added (idempotent, one "Administrador" role + one admin user) with its email/password coming from `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` (environment variables the user sets themselves in `.env`/`.env.staging`; the script never generates or logs a password on its own).
[PENDING: revisit token storage (`httpOnly` cookie) and per-request `status` verification once HU-20 (immediate lockout) is implemented; document here the decision on where to "redirect according to role" once real per-role screens exist beyond this round's `/dashboard` placeholder]

**ADR-25 — Granular authorization (HU-02): new guard per permission, bootstrap via seed, frontend still by role name**
Origin: second business story implemented (2026-08-14). Discarded: (a) extending `RolesGuard` (ADR-24) to accept module/action instead of role name — `RolesGuard` compares `user?.role` (a string embedded in the stateless JWT) against `@Roles(...)`, a comparison that requires no IO; migrating it to granular permissions would force a `RolePermission` query on every request anyway, blending two distinct responsibilities (authentication by the role declared in the token vs. authorization by a persisted permission) under one guard and stripping `RolesGuard` of the synchronous, DB-free property it has today. Both guards are kept, each with its own scope: `RolesGuard` for the simple "only this role can" case, `PermissionsGuard` (new) for "only whoever has this permission can". (b) solving the bootstrap problem manually in production (granting the first permission by hand via SQL after the first deploy) — fragile, not reproducible across environments, and contradicts that `seed.ts` (HU-01) is already the established way to leave the system in an operable state from scratch.
Solution adopted: a new `PermissionsGuard` (`backend/src/common/guards/permissions.guard.ts`), activated by `@RequirePermission(module, action)` (`backend/src/common/decorators/require-permission.decorator.ts`), registered as `APP_GUARD` inside `roles.module.ts` — the module that owns the permissions concept activates its own guard globally, same criterion as `auth.module.ts` with `JwtAuthGuard`/`RolesGuard` (ADR-24). It injects `PrismaService` directly (bypassing the `roles` module's repository), same pattern as `IdempotencyInterceptor` (ADR-21) for a cross-cutting component in `common/`; it queries `role_permission` on every marked request — no cache, acceptable at this scale (same criterion as ADR-20). Bootstrap: `backend/prisma/seed.ts` seeds 3 permissions (`roles:read`, `roles:create`, `roles:update` — only what this iteration needs, nothing speculative) and grants them to the "Administrador" role seeded by HU-01, via `rolePermission.upsert()` (idempotent thanks to the composite PK `[roleId, permissionId]`). Anyone who already ran HU-01's seed before this HU must re-run it (`npm run prisma:seed` / `prisma:seed:staging`) — without that their admin is left with zero permissions and `PermissionsGuard` blocks even creating the first new role, the exact chicken-and-egg problem this bootstrap solves. Additive migration: `Role.name` becomes `@unique` and `Permission` gains `@@unique([module, action])` — nothing to break (`RolePermission` already had a composite PK).
Explicitly accepted trade-off: the frontend (`role.guard.ts`, unchanged) still decides which route to show purely by `user.role` (a string, compared against `data: { roles: [...] }`), not by granular permission — same as already happens for `/suppliers`. No permission system is built on the client this round: it would be speculative work (no other story needs it yet) and, more importantly, the backend is already the sole real source of truth (`PermissionsGuard` denies on the server no matter what the UI does) — the frontend hiding a route is UX only, never the real protection, same principle already established for RBAC in this project.
[PENDING: once more than one role has genuinely different permissions and several screens depend on fine-grained permissions (not just "Administrador" yes/no), evaluate whether it's worth exposing the logged-in user's permissions in the JWT payload or a dedicated endpoint, so the frontend can hide UI with finer granularity than "by role name"]

**ADR-26 — User management (HU-03): `users` module owns the concept, `auth` no longer has its own repository, password change out of scope**
Origin: third business story implemented (2026-08-14), resolving the technical debt explicitly documented in `auth-user.entity.ts` since HU-01 (ADR-18): "once the `users` module exists, `auth` should consume its exported service instead of querying `User` directly via its own repository".
Discarded: (a) having `UsersModule` expose `findCredentialsByEmail(email): Promise<UserCredentialsDto|null>` with a raw `passwordHash` in the DTO, leaving `LoginUseCase` to keep doing `bcrypt.compare` — leaks the most sensitive data of the `User` aggregate outside its owning module, the same kind of leak ADR-18 tries to prevent even though it would cross via `application/dto` rather than `domain/`; it would also duplicate the "active + correct password" rule across two modules the day a second authentication flow appears. (b) keeping two parallel `User` repositories indefinitely (auth's own, scoped to login, and the new full one in `users`) — that is exactly the debt HU-01 flagged to resolve now.
Solution adopted: `UsersModule` owns the single `User` repository (`USER_REPOSITORY`/`UserPrismaRepository`) and exports `ValidateUserCredentialsUseCase.execute(email, password): Promise<AuthenticatedUserDto|null>` (`exports: [ValidateUserCredentialsUseCase]`) — it does `bcrypt.compare` and `isActive()` internally, never letting the `User` entity or its `passwordHash` leave the module. `AuthModule` becomes `imports: [PassportModule, JwtModule, UsersModule]`; `auth/domain/auth-user.entity.ts` (+spec), `auth/domain/auth-user.repository.interface.ts`, `auth/infrastructure/user.prisma.repository.ts`, and the `PrismaService` provider in `auth.module.ts` are deleted (no longer needed — `JwtStrategy` has been stateless since ADR-24). Unintended positive side effect: the generic invalid-credentials message (no enumeration) is now structurally guaranteed, since `LoginUseCase` can no longer distinguish a missing user / wrong password / blocked user — it only ever receives `null` for all three.
RBAC: `POST`/`PATCH /users` validate `roleId` against Postgres' real FK (`role_id`) without `users` querying the `roles` module — `isForeignKeyViolation()` (Prisma code `P2003`) is added to `common/utils/prisma-error.util.ts` alongside the already-existing `isUniqueConstraintViolation()` (`P2002`, reused for duplicate email). Bootstrap: same criterion as ADR-25, `users:read/create/update` seeded in `seed.ts` and granted to the "Administrador" role — anyone who already ran HU-02's seed must re-run it.
Explicitly out of scope for this HU: changing an existing user's password. `PATCH /users/:id` edits `name/email/roleId/status`, never `password` — there is no reset endpoint (no MVP1 story asks for one in section 7.4's table); left as future work instead of building something speculative now.
[PENDING: once HU-20 (lockout on failed attempts) or a future "change my password" story appear, decide whether the reset lives in `users` (an admin resets someone else's) or in a separate `account`/`profile` module (a user changes their own) — neither exists today]

**ADR-27 — Associate inventory to a location (HU-07): no dedicated endpoint, brings forward HU-08's movement engine**
Origin: fourth business story of this iteration (2026-08-16). The master plan (section 7.4, "Módulo: Inventario") assigns no endpoint of its own to HU-07 — only `POST/GET /inventory/movements` (HU-08) and `GET /inventory/stock` (HU-10) appear. The user, asked explicitly, requested a dedicated `POST /inventory/stock` to declare/initialize stock. Discarded: writing `LocationStock` directly from that endpoint — violates the rule already established in `convenciones.md` ("Inventory movements: `LocationStock` is never updated directly — always through an `InventoryMovement` record in the same transaction"). That endpoint would have to create an `InventoryMovement` anyway to not break the rule, which means building the core movement-registration mechanism right now regardless.
Solution adopted, confirmed with the user: HU-07 builds the full `POST /inventory/movements` engine (transactional: `InventoryMovement` + `LocationStock` in the same transaction, TT-17's `withOptimisticLock()`, TT-18's `@Idempotent()`/`IdempotencyInterceptor` — first real consumer of both) but **only enables the `in` type** via `@IsIn(['in'])` on `CreateMovementDto`; HU-08 simply loosens that validator to add `out`/`transfer_in`/`transfer_out`/`adjustment` on top of the same mechanism, untouched. Full hexagonal architecture (`domain/application/infrastructure`) because `convenciones.md` explicitly requires it for `inventory` (not trivial CRUD like `locations`/`products`) — `MovementRequest` (entity with behavior, ADR-17) computes the stock delta per movement type and rejects types not supported yet. `GET /inventory/stock` is also built, but deliberately "basic" (flat ids, no filters or nested product/location data) — enriching it (filters, nested objects, a frontend screen) is left to HU-10.
Technical detail: the existing-`LocationStock` lookup by `[productId, locationId, batchId]` uses `findFirst`, not `findUnique` with the compound key — Prisma's generated type for that compound key requires `batchId: string` (no `null` allowed) even though the column is nullable and Postgres' unique index does allow it (same reasoning already applied in `LocationPrismaRepository.findByParentAndName`, HU-06). A version conflict detected inside the transaction throws an internal error (`VersionConflictError`) to force Prisma to roll back the whole transaction — including the just-created `InventoryMovement` — instead of leaving it committed as an orphan while the stock update is lost; `withOptimisticLock()` catches that error as the retry signal. A location's existence is validated via the FK's `P2003` error (same as `parentId`/`unitId` in earlier HUs); no Postgres constraint can guarantee it's **active**, so `RegisterMovementUseCase` checks `Location.status` explicitly before attempting the movement.
[PENDING: once HU-08 adds `out`, decide the "insufficient stock" rule (block at negative, or allow with a warning?) — not decided yet, HU-07 didn't need it]
